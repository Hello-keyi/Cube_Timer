**核心认知（6 条）**
1. **HTTP = 客户端问服务器答（短连接）**；**WebSocket = 一次握手后全双工长连接**，服务器可主动推
2. **`ServerEndpointExporter` Bean 不注册 → `@ServerEndpoint` 完全不生效（连接 404）**
   —— 这是 Spring 第 3 个「必须显式开启」的例子（前两个：`@MapperScan`、`@EnableScheduling`）
3. **`@OnError` 方法必须接收 `Throwable`**；`@PathParam` 不能加在它上面
4. **在线连接用 `ConcurrentHashMap`；广播加 `synchronized`**（`getBasicRemote().sendText` 非线程安全）
5. **广播的 try-catch 必须放在循环内部**：单个连接失败不能影响其他连接
6. **`com.sun.*` / `sun.*` / `jdk.internal.*` 开头的 import 一律是 IDE 误补全，必须删**

**3 个预答题（学生未答，AI 补讲）**
1. 不用框架 → 只能自己 `while(true) + Thread.sleep`，问题：**重启丢失、不是整点、异常杀死线程、无法查看下次执行时间**
2. cron 六位 = **秒 分 时 日 月 周**；`0 0 2 * * ?` = 每天 02:00:00；**日和周必须有一个 `?`**
3. 多实例 → 两台机器都会执行 → 重复执行；解法：**① 分布式锁（SETNX，推荐）② 只在一台启用 ③ 幂等设计（只能兜底，防不了副作用）**

**核心认知（5 条）**
1. **`@EnableScheduling` 不加 → `@Scheduled` 静默不生效**（编译过、启动成功、任务永不执行）
2. cron 六位；`?` 表示"不关心"，用于日/周冲突
3. **`GROUP BY` 一条 SQL 算出"每个用户"的 count/min/avg**（区别于之前的单行聚合）
4. **`ON DUPLICATE KEY UPDATE`（upsert）= 幂等写入的标准写法**：无冲突则 insert，有冲突则 update
5. **MyBatis XML 里所有 SQL 的 `<` 必须写 `&lt;`**；自检命令：
   `grep -nE '<[[:space:]]|<[0-9#]' *.xml`

**新结构（对齐寒页外卖）**
```

```
server ──> common
       └─> pojo
common ⟷ pojo  （互不依赖，也都不依赖 server）

**各模块依赖**
| 模块 | 依赖 |
|---|---|

| pojo | lombok、spring-boot-starter-validation、swagger-annotations-jakarta |
| server | common、pojo、webmvc、mybatis、mysql、validation、redis、security-crypto、aspectj、pagehelper、springdoc、lombok、test |

**关键配置**
- 父 pom：`packaging=pom` + `<modules>` + `<dependencyManagement>`（common/pojo 版本统一用 `${project.version}`）
- **Lombok 的 `annotationProcessorPaths` 移到父 pom 的 `<pluginManagement>`**，三模块共享
- **`spring-boot-maven-plugin` 只放 server**（否则 common/pojo 也会被 repackage 成 fat jar）

**打包产物**
```

pojo/target/pojo-0.0.1-SNAPSHOT.jar       普通库 jar

```

**重构暴露的 2 个隐藏 bug（已修）**

| # | 问题 | 原因 | 修法 |

| 1 | `Unknown column 'created_at'` | **D19 把列改名 `create_time`，但 `todayBest` 的 XML 漏改**（只有"今天有成绩"时才执行到，一直没暴露）| XML 里 2 处 `created_at` → `create_time` |

**核心认知（6 条）**
1. **父 pom 用 `packaging=pom`**：自己不产出 jar，只负责聚合 + 统一版本
2. **版本统一放 `<dependencyManagement>`**：子模块引用时不写版本，改一处全跟着变
3. **依赖方向必须单向**：server → common / pojo；common 与 pojo 互不依赖 → 天然无循环依赖
4. **`spring-boot-maven-plugin` 只给可执行模块**（server），否则库模块被 repackage
5. **多模块最容易踩「同一库版本冲突」**：`dependency:tree` 逐模块核对是唯一可靠手段
6. **拆分的收益**：依赖边界清晰（pojo 想调 Service 直接编译不过）、编译更快、可复用、职责一目了然

**PageHelper 自动生成的 SQL（实证）**
```sql
-- 基础分页（成对出现）
SELECT count(0) FROM cube_record WHERE user_id = ?
select * from cube_record WHERE user_id = ? order by id desc LIMIT ?

-- 组合条件（条件被完整保留）
SELECT count(0) FROM cube_record WHERE user_id = ? AND time_ms >= ? AND time_ms <= ?
select * from cube_record WHERE user_id = ? and time_ms >= ? and time_ms <= ? order by id desc LIMIT ?
```
→ **业务代码一行 count 都没写**，PageHelper 解析 SQL 后自动生成 count 版本并跑两次
→ 这是「分页插件 = MyBatis 拦截器」的直接证据

**核心认知（5 条）**
1. **`startPage()` 把参数塞进 ThreadLocal，拦截器在执行第一条 SQL 时取走并清空**
   → 所以 `startPage()` 必须**紧跟**目标查询，中间不能插任何别的查询
2. **`Page<T>` 本身就是 `List` 子类**（`extends ArrayList`），序列化成 JSON 会变数组、**total 字段丢失**
   → 必须包一层 `PageInfo`（纯 POJO，含 list / total / pages / hasNextPage 等算好的导航信息）
3. **`reasonable=true` 是体感差异极大的配置**：页码越界自动回到最后一页，而不是返回空数组
4. **引入第三方 starter 必须看 `dependency:tree`**：它可能偷带一套低版本核心依赖（本次是 mybatis starter 3.x）
5. **「ThreadLocal 传上下文 + 拦截器做增强」是 Java 框架的通用套路**：
   `BaseContext`（D18/D19）、PageHelper（D20）、Spring 事务、日志 MDC、SecurityContext 全是这个模式

**已踩/预防的坑**
- 忘了 `exclusion` → mybatis 被降级到 3.x
- `startPage` 后插了别的查询 → 分页参数被抢走，查询变全表扫
- 直接返回 `Page` → 前端拿不到 total
- `reasonable` 默认 false → 越界返回空

**3 个预答题：本次未作答**（AI 已在讲解中给出答案）

**核心认知（5 条）**
1. **事务边界 = 一个完整的业务动作**，画在 Service 方法上（不是一条 SQL 一个事务）
2. **`@Transactional` 默认只回滚 `RuntimeException`**；加 `rollbackFor = Exception.class` 覆盖受检异常
3. **自增主键回填**：`<insert>` 加 `useGeneratedKeys="true" keyProperty="id"`，插入后对象上就有 id
4. **`@RequestBody` 必须配 POST / PUT**，`@GetMapping` 带请求体会报 `HttpRequestMethodNotSupportedException`
5. **事务失效 4 场景**：同类内部 `this.xxx()` 调用、方法非 public、异常被 catch 未重抛、异常类型不匹配

**寒页对照**：寒页「下单 → `orders` + `order_detail`」是同一模式；
**寒页源码里其实没写 `@Transactional`**（不规范），我们写了更规范。
