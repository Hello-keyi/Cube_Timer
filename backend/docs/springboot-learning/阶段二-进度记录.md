**实测结果（5 项全部通过）**

|---|---|---|---|
| ① | 基础分页 `page=1&size=3` | `total=22`，3 条，`ids=[31,28,26]` | ✅ |

| ⑤ | 第 3 页 | `ids=[18,17,16]` | ✅ |
| ⑥ | 控制台 ERROR | 无 | ✅ |

**PageHelper 自动生成的 SQL（实证）**
```sql
-- 基础分页（成对出现）
SELECT count(0) FROM cube_record WHERE user_id = ?
select * from cube_record WHERE user_id = ? order by id desc LIMIT ?

-- 组合条件（条件被完整保留）
SELECT count(0) FROM cube_record WHERE user_id = ? AND time_ms >= ? AND time_ms <= ?
select * from cube_record WHERE user_id = ? and time_ms >= ? and time_ms <= ? order by id desc LIMIT ?
```
→ **业务代码一行 count 都没写**，PageHelper 解析 SQL 后自动生成 count 版本并跑两次
→ 这是「分页插件 = MyBatis 拦截器」的直接证据

**核心认知（5 条）**
1. **`startPage()` 把参数塞进 ThreadLocal，拦截器在执行第一条 SQL 时取走并清空**
   → 所以 `startPage()` 必须**紧跟**目标查询，中间不能插任何别的查询
2. **`Page<T>` 本身就是 `List` 子类**（`extends ArrayList`），序列化成 JSON 会变数组、**total 字段丢失**
   → 必须包一层 `PageInfo`（纯 POJO，含 list / total / pages / hasNextPage 等算好的导航信息）
3. **`reasonable=true` 是体感差异极大的配置**：页码越界自动回到最后一页，而不是返回空数组
4. **引入第三方 starter 必须看 `dependency:tree`**：它可能偷带一套低版本核心依赖（本次是 mybatis starter 3.x）
5. **「ThreadLocal 传上下文 + 拦截器做增强」是 Java 框架的通用套路**：
   `BaseContext`（D18/D19）、PageHelper（D20）、Spring 事务、日志 MDC、SecurityContext 全是这个模式

**已踩/预防的坑**
- 忘了 `exclusion` → mybatis 被降级到 3.x
- `startPage` 后插了别的查询 → 分页参数被抢走，查询变全表扫
- 直接返回 `Page` → 前端拿不到 total
- `reasonable` 默认 false → 越界返回空

**本课核心认知（5 条）**
1. **`@Retention(RUNTIME)` 是生死线**：默认 `CLASS`，运行时就没了，切面 `getAnnotation()` 返回 null → **静默不生效**
2. **切点写法 `execution(...) && @annotation(...)`**：前者缩小到包，后者精确定位方法；缺后者会误切
3. **切面只对 `args[0]` 是实体的方法有效** → 所以 `update(Integer,Integer,Integer)` 必须改成 `update(CubeRecord)`（寒页的 update 也全收实体，原因就在这）
4. **INSERT 填 4 个字段**（create_* + update_*），**UPDATE 只填 2 个**（update_*）：新增时创建时间 = 更新时间
5. **Spring Boot 4 starter 改名**：`spring-boot-starter-aop` → `spring-boot-starter-aspectj`

- `annotation/AutoFill` ≈ 寒页 `annotation/AutoFill` ✅
- `enums/OperationType` ≈ 寒页 `enumeration/OperationType` ✅
- `aspect/AutoFillAspect` ≈ 寒页 `aspect/AutoFillAspect`（逻辑几乎一致）✅
- 差异：寒页有 `constant/AutoFillConstant` 把 `"setCreateTime"` 抽成常量；我们直接写字符串

**关键设计：越权返回「记录不存在」而不是「无权限」**
- 返回「无权限」= 告诉攻击者「这条记录存在，只是不属于你」（信息泄露）
- 返回「记录不存在」= 攻击者无法区分「真的没有」和「没权限」
- 实现方式：`update` / `deleteById` / `getById` 的 SQL 直接带 `and user_id = #{userId}`
  → **从 SQL 层就查不到**，而不是查到后再判断

**核心认知（6 条）**
1. 拦截器 `return false` 后**响应是空的**，必须自己 `response.getWriter().write(...)`；不走全局异常处理
2. `ThreadLocal` 必须在 `afterCompletion` 清理 → Tomcat 线程池复用会导致**用户串号**（随机偶发、极难排查）
3. **数据隔离要落在 SQL 上**（`where user_id = ?`），不能只在 Java 层判断
4. **缓存 key 必须带用户维度**，否则 A 用户会读到 B 用户的缓存
5. 越权访问返回「记录不存在」而非「无权限」，避免信息泄露
6. 数据迁移四步：加列（可空）→ 迁数据 → 改 NOT NULL → 建索引

**额外发现（重要）**
- **`Keys.hmacShaKeyFor()` 按密钥长度自动选算法**：32 字节 → HS256、48 字节 → HS384、64 字节 → HS512
- 本项目 secret 是 **50 字节** → 实际使用 **HS384**（不是 HS256）
- **含义**：上线后**不要随意改 secret 的长度**，否则签名算法变化 → **所有旧 token 立即失效**

**核心认知（4 条）**
1. JWT 的 Payload 是 **base64url 编码，不是加密** —— 任何人都能解开，**绝不能放敏感信息**（只放 userId 是对的）
2. 签名 = `HMAC(header.payload, secret)`；**secret 只在服务器**，所以攻击者改了 payload 也算不出新签名
3. **`@ConfigurationProperties` 的 prefix 从配置文件根级别算起**，不继承 `spring.*`；YAML 缩进错会导致「配置看起来有、实际取不到」
4. yml 缩进错的表现通常是 **NPE / 字段为 null**，而不是启动报错 —— 必须会看异常堆栈

**当前缺口**
- token 已能签发，但**没有任何接口校验它** → 谁都能调 /record/** → 第 2 部分补齐

**核心认知（5 条）**
1. **密码哈希必须「慢」**：MD5 一秒 10 亿次（几小时破解），BCrypt 一秒几十次（几百年）；`$2a$10$` 的 `10` 就是难度参数（2^10 轮）
2. **盐 = 相同密码产生不同密文**：BCrypt 自动生成盐并存在密文里，不需要手工管理；作用是防止「一张彩虹表反查所有用户」
3. **唯一性必须由数据库保证**：应用层「先查」只是友好提示，**并发场景靠 `UNIQUE KEY` 兜底**（捕获 `DuplicateKeyException`）
4. **登录失败统一提示「用户名或密码错误」**：分开提示等于告诉攻击者哪些用户名真实存在
5. **VO 里绝不能有 password**：`BeanUtils.copyProperties` 只复制同名字段，VO 没有该字段就自然不会泄漏

**修复的 1 处**
- Controller 写成了 `@GetMapping("/full")` → POST 请求报
  `HttpRequestMethodNotSupportedException: Request method 'POST' is not supported`
- **教训**：`@RequestBody` 必须配 `@PostMapping` / `@PutMapping`；GET 没有请求体。
  这个错误**启动时不报**，只有发请求才炸，且表现为「系统繁忙」。

**实测：两轮对比（教学价值最高的证据）**

| 阶段 | 请求 | 返回 | 成绩总数 | 打乱总数 | `time_ms=9999` 记录数 | 判定 |
|---|---|---|---|---|---|---|
| 初始 | — | — | 21 | 0 | — | — |
| ① 正常提交（有事务） | `{"timeMs":1234,"scrambles":["R U R2","F2 D L"]}` | `code:0` | 22 | 2 | — | ✅ |
| ② **故障注入（有事务）** | `{"timeMs":9999,"scrambles":["OK","A"×300]}` | `code:1` | **22（不变）** | **2（不变）** | **0** | ✅ **回滚成功** |
| ③ **故障注入（无事务）** | 同上 | `code:1` | **23（+1）** | 2 | **1** | ❌ **脏数据** |
| ④ 脏数据状态 | — | — | — | — | 该记录只挂 **1 条**打乱（应有 2 条） | 数据不一致 |

**结论**：无事务时，第 2 条打乱失败，但「成绩」和「第 1 条打乱」已经提交 →
数据库出现「一条成绩 + 1 条打乱」的残缺状态，而接口返回失败 —— **用户永远不会知道**。

**3 个预答题：本次未作答**（AI 已在讲解中给出答案）

**核心认知（5 条）**
1. **事务边界 = 一个完整的业务动作**，画在 Service 方法上（不是一条 SQL 一个事务）
2. **`@Transactional` 默认只回滚 `RuntimeException`**；加 `rollbackFor = Exception.class` 覆盖受检异常
3. **自增主键回填**：`<insert>` 加 `useGeneratedKeys="true" keyProperty="id"`，插入后对象上就有 id
4. **`@RequestBody` 必须配 POST / PUT**，`@GetMapping` 带请求体会报 `HttpRequestMethodNotSupportedException`
5. **事务失效 4 场景**：同类内部 `this.xxx()` 调用、方法非 public、异常被 catch 未重抛、异常类型不匹配

**寒页对照**：寒页「下单 → `orders` + `order_detail`」是同一模式；
**寒页源码里其实没写 `@Transactional`**（不规范），我们写了更规范。
