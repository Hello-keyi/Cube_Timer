#### D3 · 统一返回 `Result<T>`

> **状态：✅ 已完成（2026-10-27 验收通过）**

**目标**：所有接口返回统一结构 `{code, msg, data}`，前端不再靠 HTTP 状态码猜成败。

**为什么要**：现在业务失败（比如参数非法）只能抛 500，前端拿不到可读信息。统一返回是工程规范的第一步。

**学**
- 泛型 `<T>`：一个类装不同数据
- 静态工厂方法：`Result.success(...)` / `Result.error(...)`
- 为什么 `code=0` 表示成功（约定）

**做**
1. 新建 `common/Result.java`
2. 改 `CubeRecordController` 两个接口 → `Result<List<CubeRecord>>` / `Result<Void>`
3. 改前端 `api/records.js`：取 `json.data`，判断 `code`
4. 回归测试两条接口 + 前端页面

**代码骨架**

```java
package com.example.backend.common;

import lombok.Data;

@Data
public class Result<T> {
    private Integer code;   // 0=成功，1=失败
    private String msg;
    private T data;

    public static <T> Result<T> success(T data) {
        Result<T> r = new Result<>();
        r.setCode(0);
        r.setData(data);
        return r;
    }

    public static Result<Void> success() {
        return success(null);
    }

    public static <T> Result<T> error(String msg) {
        Result<T> r = new Result<>();
        r.setCode(1);
        r.setMsg(msg);
        return r;
    }
}
```

**验收**
- [ ] `GET /record/list` 返回 `{"code":0,"msg":null,"data":[...]}`
- [ ] `POST /record` 返回 `{"code":0,...}`
- [ ] 前端页面仍正常
- [ ] 能口述 `Result<List<CubeRecord>>` 里 data 的类型

**前端联动**：`api/records.js`

```js
export async function fetchRecords() {
  const res = await fetch(BASE_URL + '/record/list')
  const json = await res.json()
  if (json.code !== 0) throw new Error(json.msg || '读取失败')
  return json.data
}
```

**坑**
- 静态泛型方法写成 `public static Result<T> success(T data)` 少了前面的 `<T>` → 编译不过
- `Result<Void>` 和 `Result<?>` 别混
- 改了返回结构忘了改前端 → 页面白屏/报错

**3 行笔记**
1. 统一返回解决了什么问题
2. 泛型在这里省了什么代码
3. 前端怎么判断成功

#### D4 · 全局异常处理 + 自定义异常

> **状态：✅ 已完成（2026-10-29 功能 + 文案 + 3 题理解确认全部通过）**

**目标**：Service 里抛业务异常，统一被接住 → 返回 `{code:1, msg:"..."}`，而不是 500 错误页。

**为什么要**：业务失败是常态（参数不合法、记录不存在）。不加处理，前端只能看到一堆 Tomcat 报错。

**学**
- 自定义异常（继承 `RuntimeException`）
- `@RestControllerAdvice` + `@ExceptionHandler`
- 为什么 Controller 里不写 `try-catch`（统一收口）

**做**
1. `exception/BusinessException.java`
2. `handler/GlobalExceptionHandler.java`
3. `CubeRecordServiceImpl.add()` 里校验：`timeMs` 为 null 或 ≤0 → 抛 `BusinessException("成绩必须大于 0")`
4. 测试：`POST /record?timeMs=-1`

**任务分级（按 1.2 的三层）**

| 层 | 本例内容 | 你要做什么 |
|---|---|---|
| 📋 可抄 | `BusinessException` 类本体；`GlobalExceptionHandler` 的注解与整体结构 | 照抄，抄完关掉参考默写一遍 |
| 🧩 骨架 | 要接几种异常（业务异常 / 缺参数 / 兜底）；每种用哪个日志级别 | 自己判断并落笔 |
| ✍️ 必写 | 校验规则（什么算非法）、提示语文案、上限数值 | 自己想，别问我要 |


**代码骨架**

```java
public class BusinessException extends RuntimeException {
    public BusinessException(String message) { super(message); }
}
```

```java
@RestControllerAdvice
@Slf4j
public class GlobalExceptionHandler {

    @ExceptionHandler(BusinessException.class)
    public Result<Void> handleBusiness(BusinessException e) {
        log.warn("业务异常：{}", e.getMessage());
        return Result.error(e.getMessage());
    }

    @ExceptionHandler(Exception.class)
    public Result<Void> handleOther(Exception e) {
        log.error("系统异常", e);
        return Result.error("系统繁忙");
    }
}
```

**验收**
- [ ] `POST /record?timeMs=-1` 返回 `{"code":1,"msg":"成绩必须大于 0"}`
- [ ] 不传 timeMs 也有可读错误（不传会先被 Spring 拦，见「坑」）
- [ ] 控制台有 warn 日志，没有大段红色堆栈

**前端联动**：`createRecord` 也要判断 `code`，把 `msg` 显示出来。

**坑**
- 不传参数时 Spring 抛的是 `MissingServletRequestParameterException`（在进入方法之前），要在全局处理器里单独接一个
- `@ExceptionHandler(Exception.class)` 会兜住所有异常，注意别把真正的 bug 藏起来 → 用 `log.error` 打全栈

**3 行笔记**
1. 异常从 Service 抛到哪里被接住
2. 为什么 Controller 不需要 try-catch
3. 前端如何拿到错误提示

#### D5 · 分页查询

> **状态：✅ 已完成（2026-10-30 验收通过，7 条用例全过）**

**目标**：`GET /record/page?page=1&size=10` 返回 `{total, records}`。

**为什么要**：成绩会越积越多，一次全查会拖慢接口、浪费带宽。分页是所有列表接口的标配。

**学**
- 分页的本质：`select count(*)` 拿总数 + `select ... limit offset, size` 拿当页
- `PageResult` 结构：`total`（总条数）+ `records`（当页数据）
- PageHelper 的原理（拦截 SQL 自动加 limit）

**做**
1. 新建 `common/PageResult.java`
2. Mapper 加分页方法
3. Service 算 offset
4. Controller 暴露 `GET /record/page`
5. **对照控制台**确认两条 SQL

**代码骨架（不走 PageHelper 的手写版，首选方案）**

```java
// Mapper
@Select("select count(*) from cube_record")
long count();

@Select("select * from cube_record order by id desc limit #{offset}, #{size}")
List<CubeRecord> page(@Param("offset") int offset, @Param("size") int size);
```

```java
// Service
public PageResult page(int page, int size) {
    long total = cubeRecordMapper.count();
    int offset = (page - 1) * size;
    List<CubeRecord> records = cubeRecordMapper.page(offset, size);
    return new PageResult(total, records);
}
```

**验收**
- [ ] `?page=1&size=2` 只返回 2 条
- [ ] `total` 等于数据库总条数
- [ ] 翻到最后一页/超出范围不报错
- [ ] 控制台有 count + limit 两条 SQL

**前端联动**：历史页改成分页（或先只改 API 层，页面后面再跟）。

**坑**
- `limit #{offset}, #{size}` 的逗号位置；`offset` 是"跳过多少条"，不是页码
- page 从 1 开始还是 0 开始 → 自己定死，前后端统一
- 多参数必须加 `@Param`，否则 `Parameter 'offset' not found`

**备注**：如果坚持用 PageHelper，先确认它支持 Boot 4；不支持就用上面的手写版，学习目标完全一样（甚至更清楚原理）。

**3 行笔记**
1. 分页为什么要两条 SQL
2. offset 怎么算
3. total 和 records 各自给前端干什么用

#### D6 · 动态 SQL（Mapper XML）

> **状态：✅ 已完成（2026-10-31 验收通过，4 种 SQL 全部符合预期）**

**目标**：把 Mapper 从注解改成 XML，并写出带条件的查询（按时间范围 / 成绩范围筛）。

**为什么要**：真实业务的条件查询是"可选组合"的，Java 里拼 SQL 字符串既恶心又危险。XML + `<if>` 是 MyBatis 的标准解法。

**学**
- `resources/mapper/*.xml` 的结构：`namespace` + `<select id>`
- `<if>`、`<where>`（自动加 where、去掉多余 and）
- `#{}` 与 `${}` 的本质区别

**做**
1. `application.yml` 补 `mybatis.mapper-locations: classpath:mapper/*.xml`
2. 新建 `resources/mapper/CubeRecordMapper.xml`，把现有两条 SQL 迁进去（验证 XML 生效）
3. 新增条件查询方法 `search(minMs, maxMs, begin, end)`
4. 暴露 `GET /record/search?minMs=10000&maxMs=30000`
5. **对比不同参数组合**下控制台 SQL 的变化

**代码骨架**

```xml
<mapper namespace="com.example.backend.mapper.CubeRecordMapper">
    <select id="search" resultType="com.example.backend.entity.CubeRecord">
        select * from cube_record
        <where>
            <if test="minMs != null"> and time_ms &gt;= #{minMs} </if>
            <if test="maxMs != null"> and time_ms &lt;= #{maxMs} </if>
            <if test="begin != null"> and created_at &gt;= #{begin} </if>
            <if test="end != null"> and created_at &lt;= #{end} </if>
        </where>
        order by id desc
    </select>
</mapper>
```

**验收**
- [ ] 只传 `minMs` → SQL 里只有 `time_ms >= ?`
- [ ] 都不传 → SQL 里没有 `where`
- [ ] 全传 → 4 个条件都在
- [ ] 能解释 `&gt;` / `&lt;` 为什么要转义

**前端联动**：可选（历史页加筛选）。

**坑**
- **XML 里 `<` 必须写成 `&lt;`**，否则 XML 解析失败
- `namespace` 必须是接口全限定名；`id` 必须是方法名 → 否则 `Invalid bound statement`
- 方法有多参数，XML 里要用 `@Param` 的名字
- Mapper 接口里留了注解 SQL、XML 里又写一份同名 → 会冲突（同一个方法只能有一个 SQL 来源）

**3 行笔记**
1. 动态 SQL 解决了什么问题
2. `<where>` 帮我们干了什么
3. `#{}` 和 `${}` 的区别（安全角度）

#### D8 · DTO / VO 分层

> **状态：✅ 已完成（2026-11-03 验收通过，Entity 已从接口出入口消失）**

**目标**：入参用 DTO、出参用 VO，Controller 不再直接收发 Entity。

**为什么要**：Entity 是"表的照片"。直接拿它当接口出入参，会把 `id`、`created_at` 这类内部字段暴露给前端，也挡不住前端乱传字段。

**学**
- Entity（表）/ DTO（入参）/ VO（出参）的边界
- `BeanUtils.copyProperties`（同名同类型才复制）
- 为什么出参要给 `timeText`

**做**
1. `dto/CubeRecordAddDTO`（`timeMs` + 校验注解先不加）
2. `vo/CubeRecordVO`（`id`、`timeMs`、`timeText`、`createdAtText`）
3. Service 返回 VO；新增用 DTO
4. 前端直接用 `timeText`，删掉自己的 `/1000`

**代码骨架**

```java
@Data
public class CubeRecordVO {
    private Integer id;
    private Integer timeMs;
    private String timeText;      // "12.345"
    private String createdAtText; // "2026-10-22 18:27:49"
}
```

**验收**
- [ ] `GET /record/list` 的 JSON 里没有多余字段，且含 `timeText`
- [ ] 前端不再自己算秒
- [ ] 能说清三者分别出现在哪一层

**前端联动**：`format.js` 的 `formatMs` 可以删（或只留兜底）。

**坑**
- `copyProperties` 只复制**同名同类型**；类型不同会静默跳过（比如 `String` ↔ `Integer`）
- VO 里的时间格式化，注意 `LocalDateTime` → 字符串用 `DateTimeFormatter`

**3 行笔记**
1. 直接返回 Entity 有什么风险（举 2 个）

3. VO 给前端省了什么活

#### D13 · Redis 缓存

> **状态：✅ 已完成（2026-11-09 验收通过，第二次查询零 SQL）**

**目标**：`/record/stats` 走缓存（TTL 60 秒），增删改成绩时删缓存。

**为什么要**：统计是"读多写少"的典型，每次聚合全表很浪费。缓存是后端工程师必备技能。

**学**
- 缓存的意义和代价（一致性）
- key 设计：`cube:stats`
- **改数据 → 删缓存**（缓存一致性最常用策略）
- TTL 的作用（兜底，防止长期不一致）

**做**
1. `pom.xml` 加 `spring-boot-starter-data-redis`；`application.yml` 配 redis
2. 写 `service/RecordStatsService`（或直接在 Service 里）：
   - 先 `get("cube:stats")`，有就直接返回
   - 没有就查库、算完 `set` 回去（带 60s TTL）
3. `add` / `update` / `delete` 成功后 `delete("cube:stats")`
4. 用 `redis-cli` 或控制台日志验证

**验收**
- [ ] 第一次查 stats → 控制台有 SQL
- [ ] 第二次查 stats → **控制台没有 SQL**
- [ ] 新增一条成绩后再查 → SQL 又出现了（缓存被删）
- [ ] `redis-cli TTL cube:stats` 能看到剩余秒数

**前端联动**：无（契约不变）

**坑**
- 缓存了 `null` 会一直返回 null → 明确"不缓存空值"或设短 TTL
- 忘删缓存 → 前端看到旧数据（最经典 bug）
- Redis 没启动 → 启动失败或运行时异常，要能看懂报错

**3 行笔记**
1. 为什么改数据要删缓存，而不是更新缓存
2. TTL 的作用
3. 怎么证明缓存生效了（用日志/控制台）
