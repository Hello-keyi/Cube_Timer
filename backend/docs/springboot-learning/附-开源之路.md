## 开源之路

> 学生提问：「我想维护开源项目，但是我还是什么都不会呀」（2026-11-11）
> 本节回答这个问题，并给出可执行的路线。

### 15.1 先分清两件事

| 概念 | 英文 | 含义 | 现实情况 |
|---|---|---|---|
| **维护**开源项目 | maintain | 你是 owner，管 issue / PR / release / 版本 / 社区 | 通常由长期贡献者自然产生；也可以自己发起新项目 |
| **贡献给**开源项目 | contribute | 你是 contributor，提 issue / PR | **这是当前阶段该做的事** |

**结论：不要一上来想「维护」，先做「贡献」。** 几乎所有 maintainer 都是从贡献者起步的。

### 15.2 「什么都不会」的准确说法

学生已经具备（真实能力，不是自谦）：
- 从零搭建 Spring Boot + MySQL + Redis 后端并跑通（约 20 天）
- CRUD、分页、统一返回、全局异常分级、参数校验、DTO/VO 分层
- MyBatis 注解 + XML 动态 SQL、一对多建模 + 级联删除
- Redis 缓存（TTL + 主动失效 + 降级）
- 拦截器、JUnit 5 单元测试、Maven 打包可执行 jar
- 独立排查并解决 30+ 个真实问题

**真正缺失的是「在别人的代码里工作」的能力**，这是另一套技能：

| 能力 | 当前水平 | 开源需要 |
|---|---|---|
| Git | 只会 add / commit | fork、branch、PR、rebase、处理冲突、回应 review |
| 读代码 | 只读自己写的 | 在陌生大仓库里找入口、定位 bug、理解设计意图 |
| 协作沟通 | 没练过 | 写清楚的 issue / PR 描述、礼貌回应 review 意见 |
| 测试与规范 | 刚写 4 个用例 | 遵循项目既有规范、补充有意义的测试 |

> **结论：不是「什么都不会」，是「缺一套新技能」。** 而这套技能比写代码好学得多 ——
> 它更多是流程和习惯，不需要新的知识体系。

### 15.3 贡献难度阶梯（从最轻开始）

| 层级 | 做什么 | 难度 | 适合阶段 |
|---|---|---|---|
| L0 | **文档**：错别字、示例代码报错、中文翻译、README 补充 | ★ | 第一个 PR |
| L1 | **补测试**：给缺少测试的方法写单元测试 | ★★ | 刚学完 JUnit |
| L2 | **小 bug**：`good first issue` 标签的明确问题 | ★★★ | 有 1-2 个 PR 经验后 |
| L3 | **功能 / 重构**：需要和 maintainer 讨论方案 | ★★★★ | 熟悉仓库之后 |

### 15.4 四周入门计划

| 周 | 目标 | 产出 |
|---|---|---|
| 第 1 周 | 练熟 Git 协作流 | 在自己项目上完整走一遍 fork → branch → commit → push → PR |
| 第 2 周 | 学会读陌生项目 | 选一个 Java 项目，画出「请求进入 → 核心处理 → 返回」的调用链 |
| 第 3 周 | 提第一个 PR | 找 `good first issue`，从文档修正或补测试开始 |
| 第 4 周 | 开源自己的项目 | 把 Cube_Timer 推上 GitHub，写清 README 与 issue 模板 |

### 15.5 怎么选适合新手的项目

**搜索方式**
- GitHub 搜索框：`label:"good first issue" language:Java`
- 站点：up-for-grabs.net、goodfirstissue.dev、github.com/topics/good-first-issue

**筛选标准（按重要性）**
1. 仓库**近 3 个月有提交**（活跃度）
2. 有 `CONTRIBUTING.md`（说明贡献流程）
3. Star 数 **1k–10k**（太小的没人 review，太大的难上手）
4. issue 区**有人回复**（说明 maintainer 还在）
5. `good first issue` 标签里的任务**描述清晰**

### 15.6 第一个 PR 建议做什么

| 类型 | 例子 | 风险 |
|---|---|---|
| 文档错别字 / 语法 | README 里的拼写错误 | 极低 |
| 示例代码跑不通 | 文档里的示例缺 import | 低 |
| 补测试 | 某工具类没有边界测试 | 低 |
| 注释补充 | 给复杂逻辑加说明 | 低 |

**不要第一个 PR 就改核心逻辑** —— 先让 maintainer 认识你，建立信任。

### 15.7 开源协作的基本礼仪

1. **先搜 issue 再动手**（可能已经有人在做）
2. **大改动先开 issue 讨论**，不要直接提 PR
3. **PR 要小** —— 一个 PR 只做一件事
4. **commit message 写清楚**（`fix: 修正 xx 的空指针问题`）
5. **被指出问题不要辩解**，改就好 —— 这是正常的 code review
6. **跟进你提的 PR**，不要提完就消失

### 15.8 现在就能做的第一件事（10 分钟）

把 Cube_Timer 推上 GitHub，然后**在自己项目上练一遍完整 PR 流程**：

```bash
# 1) 推到 GitHub
cd ~/workplace/project/Cube_Timer
git add -A && git commit -m "feat: Cube_Timer 全栈项目完成"
git branch -M main
git remote add origin https://github.com/<你的用户名>/Cube_Timer.git
git push -u origin main

# 2) 在 GitHub 上 fork 自己的仓库 → clone fork → 建分支 → 改 README → push → 提 PR
```

**这一步不需要找项目，但能让你完整体验：fork、branch、PR、review、merge。**
第一次走通之后，给别人提 PR 就只是「换个仓库」而已。
