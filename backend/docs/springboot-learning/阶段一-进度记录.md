**3 题理解确认批改**

1. 「异常抛出来后经过哪里、被谁接住」→ **🟢 抓到了本质**
   答：`接住异常` 和 `处理异常` 是两个不同模块 —— **正确，这就是答案的核心**。
   够用版总结（不必碰 JVM 源码）：
   `Service throw` → 异常向上冒 → `Controller` 无 try-catch 继续冒 →
   **Spring 的调度层**（帮你调用 Controller 的那段代码）外面有 try-catch，**由它接住** →
   接住后再找「能处理这个异常类型的方法」→ **你写的 `GlobalExceptionHandler` 负责处理**。
   → **接住 = Spring 调度层；处理 = GlobalExceptionHandler（两个模块）**

2. 「为什么 Controller 不写 try-catch」→ **🟡 半对**
   答：可读性差、功能越界 —— 设计层面的理由 ✅
   缺机制层：不写 try-catch **不等于不处理**，异常会冒泡到调度层被统一接住。
   所以结论是：**不写是安全的；写了反而重复 + 越权**（类似「前台不处理投诉，不是没人管，而是统一转客服部」）。

3. 「缺参数时抛的是什么异常」→ **✅ 正确**
   答：`MissingServletRequestParameterException`。
   补完「为什么接不住」：`@ExceptionHandler` 按**类型**匹配，它与 `BusinessException` 无继承关系 → 匹配不上 → 落到 `Exception.class` 兜底。
   时序关键：**参数绑定发生在「进入方法体之前」**，所以 `add()` 里的 `throw new BusinessException` 根本没机会执行。

**实测证据**
- `GET /record/page?page=1&size=5` → `{"code":1,"data":null,"msg":"系统繁忙"}`
- 控制台真实异常：
  `java.lang.ClassCastException: class java.util.ArrayList cannot be cast to class com.example.backend.entity.CubeRecord`
  位置：`CubeRecordServiceImpl.java:43`

**两个认知点（重要）**

1. **强转不会改变数据的形状**：`mapper.page()` 返回的是 `List<CubeRecord>`（运行时是 `ArrayList`），
   `(CubeRecord) 列表` 想"把整个列表变成一个对象"，做不到。
   这个强转**编译期合法**（`List` 是接口，理论上可能有类同时实现 List 又继承 CubeRecord），
   **运行期才检查** → 才会出现「能编译、但一跑就炸」。

2. **兜底异常处理器会掩盖 bug**：`ClassCastException` 被 `@ExceptionHandler(Exception.class)` 接住 →
   前端只看到「系统繁忙」。
   **开发阶段看到「系统繁忙」，必须去控制台看 ERROR 堆栈**，否则永远查不到原因。

**AI 判断失误（记录下来，避免再犯）**
- 我预告「Mapper 不加 `@Param` 会报 `Parameter 'offset' not found`」→ **实际没报**。

| 回归 | list 20 条 / page total=20 | 正常 | ✅ |

**本课核心认知（4 条，都是能反复用的）**

1. **`lombok.NonNull` ≠ `jakarta.validation.constraints.NotNull`**
   - 前者让 Lombok **生成** null 检查，且被 `@RequiredArgsConstructor` 当作「必需构造参数」
     → **挤掉了无参构造器**
   - Jackson 反序列化时只能走那个单参构造器，`id` 传 null → NPE
     → `Cannot construct instance ... id is marked non-null but is null`
   - **结论：DTO 字段上的校验注解一律用 `jakarta.validation.constraints.*`**

2. **`@Valid` 让校验发生在「进入方法之前」**
   - 所以 Service 里手写的校验 `if` 可以全删（本次已删干净）
   - 但**业务状态校验必须留在 Service**：如 `rows == 0`（记录不存在）、`page <= 0`（分页参数）——
     注解只能校验"单个字段格式"，管不了"数据库里有没有这条"

3. **异常消息不能直接返回给用户**
   - `e.getMessage()` 里常带类名、包名、方法签名、SQL
   - 正确做法：**给用户固定文案，详情只写日志**
   - 本次实测泄露内容示例：
     `Required request body is missing: public com.example.backend.common.Result<java.lang.Void> com.example.backend.controller.CubeRecordController.add(...)`

4. **日志级别标准**
   | 级别 | 用在哪 | 例子 |
   |---|---|---|
   | `error` | 系统故障，需要人排查 | DB 连不上、NPE、SQL 语法错 |
   | `warn` | 可预期的问题，不用人动手 | 用户传错参数、密码错误、记录不存在 |
   | `info` | 正常业务流程 | 新增/更新/删除了一条成绩 |
   | `debug` | 调试细节 | SQL 参数、内部状态 |

> **教训**：接口里写什么名字，实现里就必须原样实现；`@Override` 报错基本等于「签名对不上」。
> **IDEA 标红时先跑 `mvn -q compile` 验证** —— 本次 IDEA 的红色**全是真错误**，不是 IDE 抽风。

3. **写缓存**：`set(STATS_KEY, JSON, Duration.ofSeconds(60))`

**关键设计**
- 每一步都 `try-catch`：**缓存是加速器不是必需品**，Redis 挂了要降级查库，不能让接口 500

4. **key 必须带命名空间**，否则不同业务会撞车；多用户场景必须带 userId
5. **IDEA 标红先跑 `mvn compile`**：命令行绿了才可能是 IDE 索引问题，命令行红了就是真错

**修复的 1 处 bug（关键）**
```java
if (start != null) { return; }   // ❌ 条件写反
if (start == null) { return; }   // ✅
```
后果：`preHandle` 一定执行 `setAttribute`，`start != null` **恒成立** → 每次直接 return →
**一条日志都不会打印**。这类 bug 不报错、不崩溃，只能靠「跑一遍看输出」发现。

**实测结果（4 条全部输出）**
```
GET  /record/list    status=200 cost=198ms
GET  /record/stats   status=200 cost=243ms
POST /record         status=200 cost=53ms
GET  /record/99999   status=200 cost=4ms
```

**学生反馈**：「抄完了，不知道什么意思」→ 已做逐行讲解

**讲解要点（已讲）**
1. `implements HandlerInterceptor` = 认领身份；接口 3 个方法都有 `default` 空实现，只重写需要的
2. `@Component` = 交给 Spring 管理（否则 `@Autowired` 报找不到 bean）；`@Slf4j` = Lombok 生成 `log`
3. **为什么用 `request.setAttribute` 而不是成员变量**：拦截器是**单例**，成员变量在并发下会串数据
4. `return true / false`：true 放行；false 直接中断（登录校验就靠这个）
5. `afterCompletion` 的 `Exception ex`：**只有未被 `@ExceptionHandler` 处理**的异常才会传进来；
   本项目全局异常处理器接走了一切，所以 `ex` 基本恒为 `null`
6. `WebMvcConfig` 的作用是**登记**（注册拦截器），不是调用；`addInterceptors` 是框架的回调点
7. 三层「横切」机制：**Filter（容器层）→ Interceptor（MVC 层，能拿到 handler）→ AOP（Bean 方法层）**

**核心认知（5 条）**
1. **框架代码靠「回调」运行**：你写方法，框架在合适时机调用你
2. **拦截器是单例** → 绝不能用成员变量存「请求级」数据
3. `postHandle` 异常时不执行、`afterCompletion` 一定执行 → 算耗时/清理必须用后者
4. **条件写反这类 bug 不报错** → 只能靠跑一遍看输出
5. 「抄完不懂」的解法：**跑一遍 → 删一行看差异 → 用自己的话写注释**
